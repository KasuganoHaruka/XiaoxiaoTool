# 医疗项目价格多版本智能查询系统 —— 设计文档 v2（重组稿）

> 版本：v2.0（基于样本实测重组）　|　状态：待评审确认　|　更新：2026-08-31
> 前序：v1.0「桌面预处理 + 内置发布」→ v1.1「用户端侧解析为主」。
> **v2 决策（已与需求方确认）**：**混合架构** + **安卓 APK 优先** + 数据模型按样本真实结构修正。
> 本稿基于对真实样本《成都市医疗服务项目价格汇编（2024版）》（1105 页、约 8500 项）的实测重写，不是对 v1.1 的措辞润色，而是把「哪一步在哪端做」按证据重新分工。

---

## 一、样本实测结论（本次重组的事实依据）

对样本 PDF 做了实际解析，得到以下影响架构与数据模型的硬事实：

| 观测 | 数据 | 结论 |
| :--- | :--- | :--- |
| 篇幅 | **1105 页，约 8500 个项目行** | 手机端逐页解析 + 逐页渲染 PNG 代价极大；桌面一次解析可复用 |
| 表格可解析性 | 随机抽 40 页，**40/40 命中表格、全部 14 列、结构完全一致** | 桌面（PyMuPDF）解析近乎已解决问题，无需在端侧重造 |
| 列结构 | **固定 14 列**（见 §四） | 与 v1.1 假设的「A/B/C 三档价」不符，需修正数据模型 |
| 价格列 | 含 `30%`、`100%`、`不超过420`、`不超过357` 等**非数字值** | 价格字段不能用纯 `numeric`，须「原文文本 + 可选解析数值」 |
| 数据性质 | 成都市官方**公开、静态**汇编 | 每个用户在手机重复解析同一份是纯浪费；宜「解析一次，多端复用」 |
| 编码体系 | 同时存在**国家码（15 位）**与**本地项目编码（9 位 + `-N` 拆分后缀）** | 需双编码建模；跨版本对齐以编码为主键线索 |

> 结论一句话：**「解析」应放桌面做一次并内置；「查询/核验/别名/版本」放手机端；「用户上传新 PDF 端侧解析」作为可选高级路径保留**。这正是 v2 的混合架构。

## 二、项目背景与核心痛点（承接 v1.1，保持不变）

日常需频繁查阅 PDF 版《医疗服务项目价格表》，现靠 `Ctrl+F` 人工定位摘录，随版本增多、名称多变而低效。

| 编号 | 痛点 |
| :--- | :--- |
| **P1** | **名称不一致**：简写/别名/顺序颠倒/英文缩写（"头部CT" vs "头颅CT平扫"），`Ctrl+F` 常漏搜。 |
| **P2** | **多版本割裂**：多份价格文件无法一屏勾选跨版本对比，只能逐个开。 |
| **P3** | **原文核验不便**：查出价格需回原文二次确认，但不能一键跳到 PDF 对应页码。 |
| **P4** | **办公电脑完全断网**：不能用任何云端 API / 在线 AI，处理须本地完成。 |
| **P5** | **移动端查阅**：常不在电脑前，期望微信小程序；**初版先安卓 APK**。 |

## 三、设计原则（4 条不可妥协）

| 原则 | 含义 | 对 v2 架构的影响 |
| :--- | :--- | :--- |
| **数据不出端** | 查询全程在用户设备完成，不调云端 API、不上传业务数据 | 检索/别名/版本全本地；解析亦本地（桌面或手机），只是**桌面预建的产物**可随 App 内置分发（公开数据，非业务上传） |
| **移动端优先** | 首要载体手机；初版安卓 APK | 交互触屏优化；内置预建 data.db，冷启动即可查 |
| **多版本并存** | P2：多份价格表并排可查、用户自管 | 数据按版本维度建模，结果带版本标签，横向分列 |
| **可迁移** | 未来迁到微信小程序，复用同一套数据与逻辑 | **技术栈选 uni-app**：一套代码先出安卓 APK，后编译小程序；数据/检索与渲染壳解耦 |

> **P4 与"内置数据"的关系澄清**：P4 只约束"工作电脑断网"。样本是官方公开内容，在联网的个人电脑上桌面解析、产出 `data.db` 后随 App 内置，属于"随包分发的公开数据"，不是"联网上传业务数据"，完全符合 P4 本意，且查询阶段零业务请求。

## 五、总体架构（v2：混合，三段解耦）

```
┌───────────────────────────────────────────────────────────────┐
│ A. 桌面数据管线（Python，联网或断网个人电脑均可，一次产出）      │
│   PyMuPDF 解析官方 PDF → 结构化(14列) → 校对报告                 │
│   产出「标准数据包 bundle」：data.db + page_images/ + meta.json  │
│                       │ 内置随 App 分发（公开数据）              │
└───────────────────────┼───────────────────────────────────────┘
                        ▼
┌───────────────────────────────────────────────────────────────┐
│ B. 安卓 APK（uni-app，手机端，用户日常使用）                    │
│   [数据层] 内置/导入 data.db（SQLite）+ page_images             │
│   [检索层] 关键词 + 拼音(全拼/首字母) + 模糊(编辑距离) + 别名扩展 │
│   [展示层] 版本勾选 / 结果横向分列 / 价格对比                    │
│   [核验层] 点结果 → 按 version+page_no 取页码图全屏（方案A）     │
│   [维护层] 自定义别名(本地生效) / 版本自管 / 导入新 bundle / 导出 │
│                       ▲                                         │
│   [可选·高级] 用户上传新 PDF → 端侧解析 → 生成同格式 bundle 落库 │
└───────────────────────┼───────────────────────────────────────┘
                        │ 未来
                        ▼  同一套 data 契约 + 检索逻辑，替换渲染壳
             ┌──────────────────────────────┐
             │ C. 微信小程序（uni-app 编译） │
             └──────────────────────────────┘
```

- **A 段（内置预建）= 主数据来源**：解决 1105 页、8500 项一次解析、人人复用。
- **B 段（安卓 APK）= 日常载体**：内置数据冷启动即查；解决 P1/P2/P3/P5。
- **B 段可选路径 = v1.1 的端侧上传解析**：面向"手上有一份系统没内置的新 PDF"，正确定位为后续高级功能，而非 M1 主路径。
- **C 段（小程序）**：uni-app 同源编译，数据与检索逻辑复用，仅换壳。

**数据流**：官方 PDF →（桌面一次）标准数据包 → 内置 App → 本地检索 → 结果 + 跳页。全程零业务网络请求、数据不出端。

## 六、标准数据包契约（bundle，解耦核心）

无论数据由「桌面管线」还是「端侧上传解析」产生，都产出同一契约，App 只认契约不认来源：

| 文件 | 用途 | 说明 |
| :--- | :--- | :--- |
| `data.db` | 结构化数据 + 索引（主检索源） | SQLite，含 FTS5 全文索引 |
| `page_images/{version}/{page_no}.webp` | 跳页核验图 | 每页压缩图，方案 A |
| `meta.json` | 版本清单、统计、解析器版本、生成时间 | App 校验兼容性 |
| `templates.json` | 列模板（列位置/表头映射） | 端侧解析复用、跨版本适配 |
| `aliases_user.csv` | 用户自定义别名（可导出/回灌） | 仅用户主动导出 |

> 图片格式建议 **WebP** 而非 PNG（同质量体积约小 25–35%，安卓原生支持），对 1105 页尤为关键。

## 七、数据模型（按样本修正）

### 7.1 item（项目主表）
| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| item_id | TEXT PK | 内部主键（hash(national_code+local_code)） |
| national_code | TEXT | 国家项目代码（15 位） |
| national_name | TEXT | 国家项目名称 |
| local_code | TEXT | 项目编码（9 位，含 `-N` 后缀） |
| name_std | TEXT | 标准名称（主检索名，取项目名称） |
| category_l1 | TEXT | 一级分类（如"综合医疗服务类"，由类目页解析） |
| connotation | TEXT | 项目内涵 |
| exclusion | TEXT | 除外内容 |
| unit | TEXT | 计价单位 |
| note | TEXT | 说明 |
| name_pinyin | TEXT | 全拼（预计算，省运行时） |
| name_initials | TEXT | 拼音首字母 |
| keywords | TEXT | 分词并集，检索辅助 |

### 7.2 price_ver（版本价格表）
| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| item_id | TEXT FK | 关联 item |
| version | TEXT | 版本标签（"2024版"…，用户可编辑） |
| price_l3a / l3b / l2a / l2b / below_l2b | TEXT | **五级医院价原文**（三甲/三乙/二甲/二乙/二乙以下） |
| price_l3a_num … below_l2b_num | REAL NULL | 可解析为纯数字时的数值（供排序/对比；`30%`/`不超过420` 则为 NULL 并保留原文） |
| price_note | TEXT | 该行价格相关说明 |
| page_no | INT | 该项目在**该版本 PDF** 中的页码（跳页用） |
| source_file | TEXT | 来源 PDF 文件名 |

> **价格存储原则**：原文文本列为主（避免 §八 溢出与信息丢失），数值列为辅仅用于能纯数字化的行。对比/排序优先用数值列，展示始终用原文列。

### 7.3 alias（别名表）
| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| alias_id | TEXT PK | |
| alias_term | TEXT | 别名/简写/缩写 |
| alias_pinyin | TEXT | 别名拼音（预计算） |
| item_id | TEXT FK | 映射到标准项目 |
| weight | INT | 置信度（自动=低，用户=高） |
| created_by | TEXT | `auto` / `user` |

### 7.4 version（版本元表）
| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| version | TEXT PK | 版本标签 |
| source_file / page_count / item_count / created_at | | 版本管理 UI 用 |

### 7.5 索引
- **FTS5**：`name_std / national_name / keywords / name_pinyin` 建全文索引，毫秒级关键词/拼音召回。
- 拼音、首字母**预计算入列**，运行时不再依赖拼音库现算。

## 八、数值精度与溢出（保留 v1.1 提醒并强化）
- 价格以**原文 TEXT 为准**，从根本上规避 `numeric(10,2)` 存大额或百分比导致的溢出/信息丢失（与既往 SQL 8115 溢出同源）。
- 辅助数值列用 `REAL`；若未来确需定点，扩到 `numeric(18,2)` 再评估。

---

## 九、智能检索与别名机制（解决 P1，纯本地 JS）

1. **输入归一**：去空格/标点、简繁统一、大小写归一。
2. **多路召回**：FTS5 精确词项 → 拼音全拼/首字母（`touluct`/`tlct`）→ 别名扩展（先查 alias 映射再召回标准名）→ 模糊（编辑距离 ≤2，Levenshtein 轻量实现）。
3. **融合排序**：精确 > 拼音 > 别名 > 模糊；同分按版本权重/命中字段。
4. **越用越准**：App 内"添加别名"入口 → 写本地 alias（`created_by=user`）→ 下次检索即生效，无需重解析；可导出 `aliases_user.csv` 备份/迁移。

---

## 十、多版本并行与版本自管（解决 P2）
- 用户上传/导入时标注版本；"版本管理"UI 增删/重命名；每版本独立 `price_ver` 行。
- 检索对所有（勾选的）版本 union，每条命中带 `version` 标签。
- 结果按项目聚合，**五级价横向分列 × 各版本**，差异一目了然；提供"仅显示有变动版本"开关。

---

## 十一、原文核验与跳页（解决 P3）

**方案 A（首版采用，最稳）**：桌面/端侧解析阶段逐页渲染为 **WebP**（~数十 KB/页）存 `page_images/{version}/`；App 点结果 → 按 `version+page_no` 取图 → 全屏预览。零域名依赖、离线可用、跳转绝对精准。

**方案 B（页数极大时升级）**：安卓可用原生 `PdfRenderer` 按 `page_no` 现渲指定页，不额外存图；**不依赖 web-view**，规避业务域名校验。检索数据两方案完全复用。

> 建议：MVP 用方案 A（内置数据包已含图）；若某 PDF 页数/体积超预期，对该版本切方案 B。

## 十三、技术栈

| 环节 | 技术 |
| :--- | :--- |
| 桌面数据管线 | Python + **PyMuPDF**（解析/渲染）；`pypinyin`；`jieba`（分词） |
| 数据产物 | **SQLite（含 FTS5）** + **WebP** 页码图 |
| App | **uni-app**（先安卓 APK，后编译微信小程序）；`pinyin-pro`（运行时兜底） |
| App 数据库 | SQLite 原生插件（安卓）/ `sql.js`（小程序端兜底） |
| 检索算法 | FTS5 + 倒排 + 拼音索引 + Levenshtein + n-gram |
| 跳页 | WebP 预渲染 + 全屏预览（方案 A）；原生 `PdfRenderer`（方案 B） |
| （可选）端侧解析 | 安卓原生插件封装 PDF 解析 / PDF.js 渲染 |
